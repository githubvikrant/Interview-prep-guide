Authentication & Authorization

🔴 Very Important
🏨
Plain English — Hotel Analogy

Authentication is like checking into a hotel — you show your ID and get a key card. That's proving who you are.

Authorization is like what doors your key card can open — the gym, your room, but not the manager's office. That's deciding what you're allowed to do.

On the web: when you log in with email + password, that's Authentication. When the app checks "can this user delete other people's posts?", that's Authorization.

⚙️ How It Works — JWT Flow

Most modern apps use JWT (JSON Web Token) for stateless authentication:

  1. User sends email + password → server verifies against DB
  2. Server signs a JWT with a secret key and sends it back
  3. Client stores JWT (httpOnly cookie is safer than localStorage)
  4. Every future request includes this JWT in the Authorization header
  5. Server verifies the JWT signature — no DB lookup needed (stateless!)
  6. For security, use short-lived access tokens (15 min) + long-lived refresh tokens (7 days)
📊 JWT Authentication Flow
sequenceDiagram participant C as 🌐 Client participant S as ⚙️ Server participant D as 🗄️ Database C->>S: POST /login {email, password} S->>D: Find user by email D-->>S: User record S->>S: bcrypt.compare(password, hash) S-->>C: { accessToken (15min), refreshToken (7d) } Note over C: Stores tokens securely C->>S: GET /api/profile (Bearer accessToken) S->>S: jwt.verify(token, SECRET) S-->>C: 200 OK { user data } Note over C,S: Access token expired? C->>S: POST /refresh { refreshToken } S->>D: Validate refresh token in DB S-->>C: New accessToken issued
javascript — Node.js / Express 
const jwt = require('jsonwebtoken');
const bcrypt = require('bcryptjs');

// LOGIN — Issue tokens
app.post('/login', async (req, res) => {
  const { email, password } = req.body;
  const user = await User.findOne({ email });
  if (!user || !await bcrypt.compare(password, user.password))
    return res.status(401).json({ error: 'Invalid credentials' });

  // Short-lived access token
  const accessToken = jwt.sign(
    { id: user._id, role: user.role },
    process.env.JWT_SECRET,
    { expiresIn: '15m' }
  );

  // Long-lived refresh token
  const refreshToken = jwt.sign(
    { id: user._id },
    process.env.REFRESH_SECRET,
    { expiresIn: '7d' }
  );

  // Store refresh token in DB (so we can revoke it)
  await Token.create({ userId: user._id, token: refreshToken });

  // Send refresh token as httpOnly cookie (XSS safe)
  res.cookie('refreshToken', refreshToken, {
    httpOnly: true, secure: true, sameSite: 'strict', maxAge: 7 * 24 * 60 * 60 * 1000
  });

  res.json({ accessToken });
});

// AUTH MIDDLEWARE
const authenticate = (req, res, next) => {
  const token = req.headers.authorization?.split(' ')[1];
  if (!token) return res.status(401).json({ error: 'No token' });
  try {
    req.user = jwt.verify(token, process.env.JWT_SECRET);
    next();
  } catch { res.status(403).json({ error: 'Invalid or expired token' }); }
};

// RBAC — Role-Based Access Control
const authorize = (...roles) => (req, res, next) => {
  if (!roles.includes(req.user.role))
    return res.status(403).json({ error: 'Forbidden' });
  next();
};

// Protected route — only admins
app.delete('/users/:id', authenticate, authorize('admin'), async (req, res) => {
  await User.findByIdAndDelete(req.params.id);
  res.json({ message: 'User deleted' });
});
🎤 Interview Q&A
Authentication verifies who you are (login with credentials). Authorization determines what you can do (permissions/roles). Auth always happens first. Example: logging into Gmail is authentication; only seeing YOUR emails is authorization.
A stolen long-lived token gives attackers permanent access. Short access tokens (15 min) limit damage if stolen. Refresh tokens are stored in httpOnly cookies (XSS-safe) and in DB (so they can be revoked/blacklisted if compromised). This gives both security AND good UX (users stay logged in without re-entering passwords).
localStorage is accessible via JavaScript, making tokens vulnerable to XSS attacks (malicious scripts can steal them). httpOnly cookies cannot be read by JavaScript at all — only sent automatically with requests. This completely eliminates the XSS token theft vector. You still need CSRF protection when using cookies.
Role-Based Access Control assigns users a role (admin, editor, viewer). Each route is protected by a middleware that checks if the user's role is in the allowed list. The role is embedded in the JWT payload on login. Example: authorize('admin', 'editor') middleware runs before the route handler and returns 403 if the role doesn't match.
JWTs are stateless — you can't truly "delete" them. Solutions: (1) Token blacklist in Redis: store invalidated token IDs until expiry; (2) Refresh token rotation: store refresh tokens in DB and delete on logout; (3) Use very short expiry (15min) to minimize the damage window. For logout, always invalidate the refresh token in the DB.
🔑 Key Takeaways
  • Always hash passwords with bcrypt (never store plain text)
  • Use short access tokens (15 min) + refresh tokens (7 days) in httpOnly cookies
  • Implement RBAC with a reusable middleware function
  • For logout: delete refresh token from DB + clear cookie
  • Use HTTPS only in production; set secure: true on cookies

Real-Time Systems

🔴 Huge Value
📱
Plain English — WhatsApp Analogy

Normal HTTP is like sending a letter — you write it, send it, wait for a reply. For a chat app, that's too slow!

WebSockets are like a phone call — once connected, both sides can talk at any time, instantly, without hanging up and calling again. This is why WhatsApp messages appear in real-time without you refreshing the page.

Socket.IO is a library that wraps WebSockets (with fallbacks) and adds rooms, namespaces, and event-based communication on top.

⚙️ WebSocket vs HTTP vs SSE
Protocol Direction Use Case
HTTP REST Client → Server only CRUD APIs, fetching data
SSE Server → Client only Live feeds, notifications
WebSocket Both directions Chat, games, collaboration
📊 Socket.IO Room-Based Chat Architecture
flowchart TD C1[👤 User A - Client] -->|socket.emit join-room| S[⚙️ Node.js Server\nSocket.IO] C2[👤 User B - Client] -->|socket.emit join-room| S C3[👤 User C - Client] -->|socket.emit join-room| S S --> R1[🏠 Room: general] S --> R2[🏠 Room: project-42] R1 -->|io.to.emit new-message| C1 R1 -->|io.to.emit new-message| C2 R2 -->|io.to.emit new-message| C3 S <-->|Pub/Sub for scaling| Redis[(🔴 Redis\nAdapter)]
javascript — Socket.IO Server + Client 
// ── SERVER (server.js) ──
const { createServer } = require('http');
const { Server } = require('socket.io');
const app = require('./app');

const httpServer = createServer(app);
const io = new Server(httpServer, {
  cors: { origin: process.env.CLIENT_URL, credentials: true }
});

// Auth middleware for sockets
io.use((socket, next) => {
  const token = socket.handshake.auth.token;
  try {
    socket.user = jwt.verify(token, process.env.JWT_SECRET);
    next();
  } catch { next(new Error('Unauthorized')); }
});

io.on('connection', (socket) => {
  console.log(`User connected: ${socket.user.id}`);

  // Join a room (e.g., a chat channel or board)
  socket.on('join-room', (roomId) => {
    socket.join(roomId);
    socket.to(roomId).emit('user-joined', { userId: socket.user.id });
  });

  // Handle incoming messages
  socket.on('send-message', async ({ roomId, text }) => {
    const msg = await Message.create({ roomId, text, userId: socket.user.id });
    // Broadcast to everyone in the room (including sender)
    io.to(roomId).emit('new-message', msg);
  });

  // Typing indicator (no DB needed — just broadcast)
  socket.on('typing', ({ roomId }) => {
    socket.to(roomId).emit('user-typing', { userId: socket.user.id });
  });

  socket.on('disconnect', () => {
    console.log(`User disconnected: ${socket.user.id}`);
  });
});

// ── CLIENT (React) ──
import { io } from 'socket.io-client';

const socket = io('http://localhost:5000', {
  auth: { token: localStorage.getItem('accessToken') }
});

socket.emit('join-room', 'general');
socket.on('new-message', (msg) => setMessages(prev => [...prev, msg]));
🎤 Interview Q&A
HTTP polling: client repeatedly asks the server "any updates?" every X seconds — wasteful, high latency. Long polling: client asks, server holds the connection open until there's data — better, but still HTTP overhead. WebSockets: one persistent TCP connection established via HTTP upgrade — server can push data instantly with no repeated handshakes. Much lower latency and bandwidth usage.
A single Socket.IO server can't share socket state with other server instances. Solution: use the Socket.IO Redis Adapter (@socket.io/redis-adapter). All server instances subscribe to the same Redis Pub/Sub channel. When one server emits to a room, Redis broadcasts it to all servers, which then relay it to their local connected clients. This allows horizontal scaling.
Rooms are logical groupings of sockets within a namespace. A socket can join multiple rooms. io.to('room1').emit() sends only to sockets in that room. Perfect for chat channels or boards. Namespaces are separate communication channels on the same server (like /chat vs /notifications). Each namespace has its own events, rooms, and middleware.
Use Server-Sent Events (SSE) when you only need server-to-client communication (one direction) — e.g., live dashboards, news feeds, progress bars. SSE works over regular HTTP, is easier to implement, and automatically reconnects. Use WebSockets when you need bidirectional communication (e.g., chat, collaborative editing). SSE is simpler and more firewall-friendly for one-way use cases.
You can't set custom headers on browser WebSocket connections. Two approaches: (1) Pass the JWT in the Socket.IO auth object during connection: io({ auth: { token } }) and verify it in a socket middleware on the server. (2) Use a short-lived "socket ticket" — REST endpoint issues a one-time ticket, client passes it in the WebSocket URL query param. Never put tokens in URL query params in production.
🔑 Key Takeaways
  • WebSockets = full-duplex persistent TCP connection (vs HTTP request/response)
  • Use rooms to broadcast to groups of users
  • Scale with Redis Adapter for multi-server deployments
  • Authenticate sockets using Socket.IO auth middleware
  • SSE for one-way server push; WebSockets for bidirectional

Database Design

🔴 Extremely Important
📚
Plain English — Library Analogy

A database is like a huge library. Schema design is deciding how to organize the shelves — do you put all books by one author together (embedding), or give each book its own catalog card that points to the author section (referencing)?

Indexing is like the card catalog — without it, you'd have to walk every single aisle to find one book. With it, you jump straight to the right shelf. Aggregation is like asking the librarian "how many books were borrowed this month?" — complex queries that summarize data.

⚙️ Embedding vs Referencing in MongoDB
Strategy When to Use Example
Embed Data always loaded together, small/bounded arrays User → address, Post → tags
Reference Data accessed independently, large/unbounded arrays Post → author (User), Comment → Post
📊 MongoDB Schema Design — Blog Platform
erDiagram USER { ObjectId _id string name string email string passwordHash string role date createdAt } POST { ObjectId _id string title string content ObjectId authorId string[] tags int viewCount date createdAt } COMMENT { ObjectId _id string text ObjectId postId ObjectId userId date createdAt } USER ||--o{ POST : "writes" POST ||--o{ COMMENT : "has" USER ||--o{ COMMENT : "writes"
javascript — Mongoose Schema + Indexing + Aggregation 
// ── SCHEMA WITH INDEXES ──
const postSchema = new mongoose.Schema({
  title: { type: String, required: true },
  content: { type: String, required: true },
  author: { type: mongoose.Schema.Types.ObjectId, ref: 'User', required: true },
  tags: [String],
  viewCount: { type: Number, default: 0 },
  createdAt: { type: Date, default: Date.now }
});

// Compound index for common query pattern
postSchema.index({ author: 1, createdAt: -1 });
// Text index for full-text search
postSchema.index({ title: 'text', content: 'text' });

// ── EFFICIENT QUERY ──
// Pagination with sorting (much faster with index)
const posts = await Post.find({ author: userId })
  .sort({ createdAt: -1 })
  .skip((page - 1) * limit)
  .limit(limit)
  .populate('author', 'name email'); // JOIN equivalent

// ── AGGREGATION PIPELINE ──
// "Get top 5 authors by post count this month"
const topAuthors = await Post.aggregate([
  { $match: { createdAt: { $gte: new Date(Date.now() - 30 * 24 * 60 * 60 * 1000) } } },
  { $group: { _id: '$author', postCount: { $sum: 1 }, totalViews: { $sum: '$viewCount' } } },
  { $sort: { postCount: -1 } },
  { $limit: 5 },
  { $lookup: { from: 'users', localField: '_id', foreignField: '_id', as: 'authorInfo' } },
  { $unwind: '$authorInfo' },
  { $project: { name: '$authorInfo.name', postCount: 1, totalViews: 1 } }
]);
🎤 Interview Q&A
Embed when: data is always read together (1:1 or 1:few), the array is bounded and small, denormalization is acceptable. Example: user + address. Reference when: data is accessed independently, arrays are unbounded (comments on a viral post), or data is shared across documents. The "16MB document limit" rule: if embedding would grow documents unboundedly, always reference.
An index is a data structure (B-tree) that MongoDB maintains separately from the collection. It stores a sorted copy of one or more fields with pointers to the full documents. Without an index, every query does a COLLSCAN (read every document). With an index, it does an IXSCAN (jump to the right documents). Trade-off: indexes speed up reads but slow down writes (index must be updated on every insert/update). Use explain('executionStats') to verify indexes are being used.
The aggregation pipeline is a sequence of stages, each transforming the data. Key stages: $match (filter, like WHERE), $group (like GROUP BY), $sort, $limit, $lookup (like SQL JOIN), $project (select fields), $unwind (flatten arrays). Data flows stage-by-stage — always put $match first to reduce data early. Put $match before $lookup to minimize data sent to the join.
Two approaches: (1) Offset pagination: .skip(page * limit).limit(limit) — simple but slow for large offsets (MongoDB must scan all skipped docs). (2) Cursor pagination: use the last document's _id or timestamp as a cursor: find({ _id: { $gt: lastId } }).limit(limit) — O(log n) regardless of page, better performance. Cursor pagination is preferred for large datasets. Always create an index on the sort field.
A compound index covers multiple fields: { author: 1, createdAt: -1 }. It satisfies queries that filter on author alone OR on author + createdAt together (left-prefix rule). Use when your most common queries filter on multiple fields. The order matters — put equality fields first, then range/sort fields. One compound index can replace multiple single-field indexes for related queries.
🔑 Key Takeaways
  • Embed for 1:few bounded data; Reference for 1:many unbounded data
  • Always index fields you sort, filter, or join on
  • Use explain() to confirm indexes are used in queries
  • Aggregation pipeline: always $match first, then $group, $lookup, $project
  • Use cursor pagination for performance on large collections

Caching with Redis

🔴 Huge Differentiator
🧠
Plain English — Short-Term Memory Analogy

Imagine you're a chef. Every time a customer orders "Caesar salad," you walk to the storage room, get lettuce, croutons, dressing, prepare everything from scratch. That's hitting the database every time.

Redis is your prep station — you pre-make 20 Caesar salads and keep them ready. When the order comes, you serve instantly. When they run out (cache expires), you make a fresh batch.

Redis is an in-memory key-value store — data lives in RAM (not disk), so reads are ~0.1ms vs ~10ms for MongoDB. Perfect for frequently read, rarely changing data.

📊 Cache-Aside Pattern (Most Common)
flowchart TD A[📱 Client Request] --> B{🔴 Redis\nCache HIT?} B -->|✅ Yes - Cache Hit| C[Return cached data\n~0.1ms] B -->|❌ No - Cache Miss| D[🗄️ Query MongoDB\n~10ms] D --> E[Store result in Redis\nwith TTL expiry] E --> F[Return data to client] C --> G[⚡ Response to Client] F --> G H[✏️ Data Updated] --> I[Invalidate/Update\nRedis cache key]
javascript — Redis Cache-Aside + Session + Rate Limiting 
const redis = require('redis');
const client = redis.createClient({ url: process.env.REDIS_URL });
await client.connect();

// ── CACHE-ASIDE PATTERN ──
async function getCachedData(key, fetchFn, ttlSeconds = 300) {
  // 1. Check cache
  const cached = await client.get(key);
  if (cached) return JSON.parse(cached);

  // 2. Cache miss — fetch from DB
  const data = await fetchFn();

  // 3. Store in cache with TTL
  await client.setEx(key, ttlSeconds, JSON.stringify(data));
  return data;
}

// Usage
app.get('/api/posts', async (req, res) => {
  const posts = await getCachedData(
    'posts:all',
    () => Post.find().populate('author', 'name').lean(),
    60 // 60 second TTL
  );
  res.json(posts);
});

// Invalidate cache when data changes
app.post('/api/posts', authenticate, async (req, res) => {
  const post = await Post.create({ ...req.body, author: req.user.id });
  await client.del('posts:all'); // Bust the cache
  res.status(201).json(post);
});

// ── RATE LIMITING WITH REDIS ──
const rateLimit = (limit, windowSec) => async (req, res, next) => {
  const key = `rate:${req.ip}`;
  const current = await client.incr(key);
  if (current === 1) await client.expire(key, windowSec);
  if (current > limit) return res.status(429).json({ error: 'Too many requests' });
  next();
};

// Apply: max 100 requests per 60 seconds
app.use('/api', rateLimit(100, 60));

// ── SESSION STORAGE ──
const session = require('express-session');
const RedisStore = require('connect-redis').default;
app.use(session({
  store: new RedisStore({ client }),
  secret: process.env.SESSION_SECRET,
  resave: false, saveUninitialized: false,
  cookie: { secure: true, maxAge: 24 * 60 * 60 * 1000 }
}));
🎤 Interview Q&A
Cache-Aside (Lazy Loading): application checks cache first. On miss, fetches from DB, stores in cache, returns. On hit, returns cached data. Best for read-heavy data (product listings, user profiles, board data). Trade-off: first request is always slow (cold start). Other patterns: Write-Through (update cache and DB simultaneously on write — consistent but slower writes), Write-Behind (update cache, async write to DB — fast writes but risk of data loss).
Cache invalidation is deciding when to remove or update cached data so clients don't get stale results. It's hard because: (1) Time-based TTL: simple but users may see stale data for up to TTL seconds; (2) Event-driven invalidation: delete cache key on data update — consistent but you must track all cache keys that depend on changed data; (3) Cache stampede: if TTL expires, many requests hit DB simultaneously. Solutions: use lock (mutex), background refresh, or staggered TTLs.
Strings: simple key-value, counters (INCR). Hashes: like objects (HSET user:1 name "John"). Lists: ordered, push/pop from both ends — job queues. Sets: unique values — online users, tags. Sorted Sets: values with scores — leaderboards, priority queues. Pub/Sub: messaging between services. Right data structure = massive performance gains.
Use Redis INCR + EXPIRE. On each request: increment a counter keyed to the user's IP (or user ID). Set expiry on first increment. If counter exceeds limit, return 429. This is atomic and works across multiple server instances (unlike in-memory rate limiting). More precise alternative: sliding window using sorted sets — store timestamps of recent requests and count within the window.
Redis Pub/Sub is a messaging pattern where publishers send messages to channels and subscribers receive them. Used for: (1) Socket.IO scaling — broadcast events across multiple server instances; (2) Microservice events — "user signed up" triggers welcome email service; (3) Cache invalidation — one service publishes "data changed", others invalidate their caches. Unlike message queues, Pub/Sub is fire-and-forget — messages are lost if no subscriber is connected at that moment.
🔑 Key Takeaways
  • Redis is in-memory — ~100x faster than DB for reads
  • Cache-Aside = check cache → miss → fetch DB → store → return
  • Always set a TTL to prevent stale data from living forever
  • Use Redis for: caching, sessions, rate limiting, queues, Pub/Sub
  • Cache invalidation: delete on write for consistency over TTL-only

Async & Backend Architecture

🔴 Critical
🍕
Plain English — Restaurant Kitchen Analogy

Node.js is like a single chef who is extremely efficient. Instead of waiting at the oven for the pizza to bake (blocking), he starts the pizza, then immediately takes another order, then checks on the pasta. He never stands idle — that's the Event Loop.

But some jobs are too heavy — like making 1000 sandwiches. You don't want the chef (main thread) doing that during dinner rush. You hand that to a separate kitchen (job queue) — like BullMQ — that processes it in the background. The chef just drops a ticket and moves on.

📊 Node.js Event Loop + Job Queue Architecture
flowchart LR A[HTTP Request] --> B[Node.js\nEvent Loop\nSingle Thread] B --> C{Async\nOperation?} C -->|DB / File / Network| D[libuv Thread Pool\nor OS async] D -->|Callback| B B --> E[Response to Client] B -->|Heavy Job\nemail/AI/image| F[BullMQ\nJob Queue] F --> G[Redis\nJob Store] G --> H[Worker Process\nBackground Thread] H -->|Done| I[Job Complete\nNotify via Socket]
javascript — BullMQ Job Queue (Email + AI Worker) 
const { Queue, Worker } = require('bullmq');
const redisConfig = { connection: { host: 'localhost', port: 6379 } };

// ── PRODUCER: Add jobs to queue ──
const emailQueue = new Queue('emails', redisConfig);

app.post('/register', async (req, res) => {
  const user = await User.create(req.body);
  
  // Don't block the response — add to queue and return immediately
  await emailQueue.add('welcome-email', {
    to: user.email,
    name: user.name,
    userId: user._id.toString()
  }, {
    attempts: 3,        // Retry 3 times on failure
    backoff: { type: 'exponential', delay: 2000 } // 2s, 4s, 8s
  });

  res.status(201).json({ message: 'Registered! Welcome email on its way.' });
  // Email will be sent by worker in background — user gets response instantly
});

// ── CONSUMER: Worker processes jobs ──
const emailWorker = new Worker('emails', async (job) => {
  if (job.name === 'welcome-email') {
    await sendEmail({
      to: job.data.to,
      subject: 'Welcome!',
      html: `<h1>Hi ${job.data.name}!</h1><p>Thanks for joining.</p>`
    });
    console.log(`✅ Welcome email sent to ${job.data.to}`);
  }
}, redisConfig);

emailWorker.on('failed', (job, err) => {
  console.error(`❌ Job ${job.id} failed:`, err.message);
});

// ── EVENT LOOP — Understanding Callbacks vs Promises ──
// Callback Hell (bad)
getUser(id, (user) => {
  getPosts(user.id, (posts) => {
    getComments(posts[0].id, (comments) => { /* nested hell */ });
  });
});

// Promise Chain (better)
getUser(id).then(user => getPosts(user.id)).then(posts => getComments(posts[0].id));

// Async/Await (best — reads like sync code)
const user = await getUser(id);
const posts = await getPosts(user.id);
const comments = await getComments(posts[0].id);

// Run in parallel when independent
const [user, settings] = await Promise.all([getUser(id), getSettings(id)]);
🎤 Interview Q&A
Node.js is single-threaded but non-blocking. The Event Loop continuously checks: (1) Call Stack — execute synchronous code; (2) Microtask Queue — Promises/async callbacks (processed after each call stack item); (3) Macro Task Queue — setTimeout, setInterval, I/O callbacks. When async operations (DB queries, file reads) complete, their callbacks are pushed to the queue. This allows Node.js to handle thousands of concurrent connections without creating a thread per connection.
A job queue (BullMQ, Agenda) allows you to defer time-consuming tasks to background workers. Use when: sending emails, processing images/videos, calling slow AI APIs, generating reports, sending bulk notifications. Benefits: (1) Faster API responses (don't wait for slow operations); (2) Automatic retries on failure; (3) Rate limiting — don't overwhelm external APIs; (4) Visibility into job status; (5) Can scale workers independently. Redis backs BullMQ as the job store.
Promise.all: runs promises in parallel, resolves when ALL resolve. If ANY reject, it immediately rejects (fail-fast). Use when all operations are required. Promise.allSettled: waits for ALL to complete regardless of success/failure. Returns array of {status, value/reason}. Use when you want results from all operations even if some fail. Promise.race: resolves/rejects as soon as the FIRST promise settles — good for timeouts.
Blocking operations prevent the event loop from processing other requests. Examples: CPU-intensive loops, synchronous file reads (fs.readFileSync), heavy JSON parsing, image processing. Solutions: (1) Use async versions (fs.readFile); (2) Offload to Worker Threads (worker_threads module) for CPU work; (3) Use job queues for heavy tasks; (4) Use setImmediate to break up long loops. Never use blocking operations in request handlers.
🔑 Key Takeaways
  • Node.js is single-threaded non-blocking — Event Loop handles concurrency
  • Offload slow tasks (email, AI, image) to job queues (BullMQ)
  • Use Promise.all to run independent async ops in parallel
  • Never block the event loop — use async I/O, Worker Threads, or queues
  • Async/Await is just syntactic sugar over Promises — same behavior

System Design Thinking

🔴 Most Important
🏙️
Plain English — City Planning Analogy

Building software at scale is like planning a city. You don't build one giant building for everyone — you have hospitals, schools, shops, each with their own purpose (microservices). You have roads connecting them (APIs). Traffic lights manage flow (load balancers). Water towers pre-store water so pipes don't run dry on demand (caching).

System Design interviews test whether you can think like a city planner — handle growth, failure, and scale — not just write code for one building.

📊 Scalable Web App Architecture

# SYSTEM DESIGN INTERVIEW FRAMEWORK (4 Steps)

# STEP 1: Clarify Requirements (5 min)
# - Scale: how many users? DAU? Read/write ratio?
# - Features: what are the top 3 features to design?
# - Constraints: latency requirements? Consistency vs availability?

# STEP 2: High-Level Design (10 min)
# - Client → CDN → Load Balancer → API Servers → Cache → DB
# - Identify services, data flows, APIs

# STEP 3: Deep Dive on Components (15 min)
# - Database schema decisions
# - Caching strategy (what to cache, TTL, invalidation)
# - How to handle scale: horizontal scaling, sharding, replication

# - Bottlenecks? Single points of failure?
# - How do you handle 10x traffic spike?
# - What if DB goes down? (Read replicas, circuit breakers)

# KEY CONCEPTS TO KNOW:
# Horizontal Scaling: Add more servers (stateless design required)
# Vertical Scaling: Bigger server (has limits, expensive)
# Load Balancing: Round-robin, least-connections, IP hash
# Database Replication: Primary (writes) + Replicas (reads)
# Sharding: Split DB by key (userId % 4) across multiple DBs
# CAP Theorem: Can't have Consistency + Availability + Partition tolerance all at once
🎤 Interview Q&A
Vertical scaling: upgrade the server (more RAM, CPU). Simple but has limits and creates single point of failure. Horizontal scaling: add more servers behind a load balancer. Requires stateless application design (sessions in Redis, not in-memory). Much more scalable — used by all major companies. For databases: read replicas handle read scale, sharding handles write scale.
A distributed system can guarantee at most 2 of 3: Consistency (all nodes see the same data), Availability (every request gets a response), Partition Tolerance (system works despite network splits). Since network partitions always happen in distributed systems, you choose CA or CP: MongoDB chooses CP (consistency over availability). Redis chooses AP (availability over strict consistency). Design based on your needs — financial systems need CP; social feeds can accept AP.
A Content Delivery Network is a network of globally distributed servers that cache and serve static assets (images, CSS, JS, HTML) from the server closest to the user. Benefits: (1) Reduced latency — user in Mumbai gets assets from Mumbai server, not USA; (2) Reduced load on origin server; (3) DDoS protection. Use for: static files, images, video, Next.js static pages. Cloudflare and AWS CloudFront are common CDNs.
Monolith: all features in one codebase/deployment. Simple to develop, deploy, debug. Becomes problematic at scale — one bug can bring down everything; can't scale individual parts. Microservices: split into independent services (Auth, Orders, Notifications). Each deploys independently, scales independently, uses its own DB. Trade-off: much more complex (network calls, distributed tracing, service discovery). Start with a modular monolith, extract services when you actually need to scale them.
🔑 Key Takeaways
  • System Design framework: Clarify → High-Level → Deep Dive → Scale
  • Stateless servers + Redis sessions = horizontal scaling friendly
  • CDN for static assets; Load Balancer for API servers
  • Read replicas scale reads; Sharding scales writes
  • Start with modular monolith, graduate to microservices when needed

File Storage & Upload Systems

🟠 Very Useful
📮
Plain English — Post Office Analogy

Your server is like a post office counter. When a customer (user) hands you a parcel (file), you don't keep it at the counter — the counter would get jammed. You send it to a warehouse (Cloudinary / S3) that's built for storage.

The customer gets a tracking number (URL) to retrieve the parcel later. Your counter stays free to handle more customers. This is why you never store files directly on your server — use cloud storage.

📊 File Upload Flow — Multer → Cloudinary

const multer = require('multer');
const cloudinary = require('cloudinary').v2;
const { CloudinaryStorage } = require('multer-storage-cloudinary');

cloudinary.config({
  cloud_name: process.env.CLOUDINARY_CLOUD_NAME,
  api_key: process.env.CLOUDINARY_API_KEY,
  api_secret: process.env.CLOUDINARY_API_SECRET,
});

// ── OPTION 1: Stream directly to Cloudinary (no local disk) ──
const storage = new CloudinaryStorage({
  cloudinary,
  params: {
    folder: 'interview-prep/avatars',
    allowed_formats: ['jpg', 'png', 'webp'],
    transformation: [{ width: 400, height: 400, crop: 'fill' }], // Auto resize
  },
});

const upload = multer({
  storage,
  limits: { fileSize: 5 * 1024 * 1024 }, // 5MB limit
  fileFilter: (req, file, cb) => {
    const allowed = ['image/jpeg', 'image/png', 'image/webp'];
    if (!allowed.includes(file.mimetype))
      return cb(new Error('Only JPEG/PNG/WebP images allowed'), false);
    cb(null, true);
  },
});

// Single file upload
app.post('/api/avatar', authenticate, upload.single('avatar'), async (req, res) => {
  const user = await User.findByIdAndUpdate(
    req.user.id,
    { avatar: req.file.path }, // Cloudinary URL stored in DB
    { new: true }
  );
  // Delete old avatar from Cloudinary if it exists
  if (user.oldAvatarId) await cloudinary.uploader.destroy(user.oldAvatarId);
  res.json({ avatarUrl: req.file.path });
});

// Multiple files (e.g., task attachments)
app.post('/api/tasks/:id/attachments', authenticate, upload.array('files', 5), async (req, res) => {
  const urls = req.files.map(f => ({ url: f.path, name: f.originalname }));
  await Task.findByIdAndUpdate(req.params.id, { $push: { attachments: { $each: urls } } });
  res.json({ attachments: urls });
});

// ── OPTION 2: Memory buffer → upload programmatically ──
const memUpload = multer({ storage: multer.memoryStorage(), limits: { fileSize: 10 * 1024 * 1024 } });
app.post('/api/upload-doc', memUpload.single('doc'), async (req, res) => {
  const result = await new Promise((resolve, reject) => {
    cloudinary.uploader.upload_stream({ folder: 'docs', resource_type: 'raw' }, (err, r) => {
      err ? reject(err) : resolve(r);
    }).end(req.file.buffer);
  });
  res.json({ url: result.secure_url });
});
🎤 Interview Q&A
Three reasons: (1) Scalability — if you horizontally scale to multiple servers, only one server has the file; (2) Persistence — servers on platforms like Heroku/Render have ephemeral file systems (files deleted on restart); (3) Performance — serving large files through Node.js blocks the event loop and uses server bandwidth. Cloud storage (Cloudinary, S3) solves all three: globally distributed, persistent, and clients download directly from CDN without touching your server.
Never trust the file extension alone — it can be faked. Validate: (1) MIME type via file.mimetype in Multer's fileFilter (check against allowlist); (2) File size via limits.fileSize; (3) Magic bytes (file signature) using a library like file-type to verify the actual file content matches the claimed type; (4) Virus scanning for sensitive apps using ClamAV or VirusTotal API. Also always generate a new filename server-side — never use the original user-provided filename.
A pre-signed URL is a temporary, time-limited URL that allows a client to upload directly to S3/Cloudinary without routing the file through your server. Flow: (1) Client requests an upload URL from your server; (2) Server generates a signed URL using AWS SDK (valid for e.g. 15 minutes); (3) Client uploads directly to S3 using that URL; (4) Client notifies your server with the file key. Benefit: your server never handles the file bytes — reduces load and cost. Best for large files or high-volume uploads.
Chunked uploads: split large files into chunks on the client, upload each chunk separately, reassemble on the server or cloud storage. Supports pause/resume. Use pre-signed URLs for direct S3 multipart upload. Stream processing: instead of loading the entire file into memory with memoryStorage, use diskStorage or pipe directly to cloud storage — much lower memory footprint. For videos, upload to Cloudinary and use their transcoding pipeline.
🔑 Key Takeaways
  • Never store files on your server — use Cloudinary or S3
  • Validate MIME type + file size in Multer's fileFilter
  • Store only the cloud URL in MongoDB, not the file itself
  • Use pre-signed URLs for large files (bypass server entirely)
  • Always generate server-side filenames — never trust user-provided names

Security

🔴 Massive Differentiator
🏰
Plain English — Castle Defence Analogy

A secure app is like a well-defended castle. The moat (HTTPS) prevents eavesdropping. The drawbridge guard (Helmet headers) checks everyone entering. The archers (rate limiting) slow down attackers. The secret compartments (input validation) prevent anyone from sneaking in through hidden passages (injection attacks).

Security is not one thing — it's layers. Each layer alone isn't enough; together they make breaching extremely difficult.

📊 Security Layers in a Node.js App

const helmet = require('helmet');
const cors = require('cors');

// Sets: X-Content-Type-Options, X-Frame-Options, Content-Security-Policy, etc.

app.use(cors({

🎤 Interview Q&A
Cross-Site Scripting (XSS): attacker injects malicious JavaScript into your app (e.g., via a comment field). When other users view that content, the script executes in their browser — stealing cookies/tokens. Prevention: (1) Escape output — React does this automatically; (2) Sanitize input — strip HTML tags on server with xss-clean; (3) Content Security Policy via Helmet — tells browser which scripts to trust; (4) httpOnly cookies — prevent JS from reading auth tokens even if XSS occurs.
Cross-Site Request Forgery: malicious website tricks a logged-in user's browser into making requests to your API (cookies are sent automatically). Prevention: (1) SameSite cookies: sameSite: 'strict' — browser won't send cookies on cross-site requests; (2) CSRF tokens: hidden token in forms, verified server-side; (3) Check Origin/Referer headers; (4) Using Authorization header (Bearer token) instead of cookies — cross-site requests can't set custom headers, so no CSRF risk. Modern APIs using JWT in headers + CORS are naturally CSRF-safe.
Injection attacks insert malicious query operators into inputs. Classic SQL: '; DROP TABLE users;--. NoSQL (MongoDB): { "email": { "$gt": "" } } bypasses login by matching ALL users. Prevention: (1) Use an ORM/ODM (Mongoose) — queries are parameterized, not raw strings; (2) Use express-mongo-sanitize — removes $ and . from request body; (3) Validate input with Zod/Joi — reject non-string email values; (4) Principle of least privilege — DB user should only have permissions it needs.
X-Content-Type-Options: nosniff — prevents browsers from guessing MIME types (MIME sniffing attacks). X-Frame-Options: DENY — prevents clickjacking (your app embedded in an iframe on a malicious site). Content-Security-Policy — whitelist trusted script/style sources, blocks inline XSS. Strict-Transport-Security (HSTS) — forces HTTPS even if user types http://. X-XSS-Protection — enables browser's built-in XSS filter. One line app.use(helmet()) enables all of these.
Never hardcode secrets in source code. Best practices: (1) Store in .env file locally — add to .gitignore immediately; (2) Use dotenv to load them (require('dotenv').config()); (3) In production: use platform environment variables (Render, Railway settings) or a secrets manager (AWS Secrets Manager, HashiCorp Vault); (4) Rotate secrets regularly; (5) Use different secrets for dev/staging/production; (6) Audit git history if a secret was accidentally committed — consider it compromised and rotate immediately.
🔑 Key Takeaways
  • Helmet = 7+ security headers in one line
  • Validate ALL input with Zod before it touches your DB
  • XSS → escape output + httpOnly cookies + CSP headers
  • CSRF → SameSite cookies or Bearer token auth (not cookies for APIs)
  • NoSQL injection → express-mongo-sanitize + Mongoose ORM
  • Secrets → .env locally, platform env vars in production, never in code

Docker & Containerization

🟠 Very High Value
📦
Plain English — Shipping Container Analogy

Before shipping containers, loading a ship was chaos — each item needed different handling. After standardized containers, everything packed into the same-sized box that ships, trucks, and cranes all know how to handle.

Docker containers do the same for software. Your app, its Node version, its dependencies — all packed into one container. "Works on my machine" becomes irrelevant because the container runs identically everywhere: your laptop, your colleague's Windows machine, and your Ubuntu production server.

🎤 Interview Q&A
An image is a read-only blueprint — like a class in OOP. It contains the OS, runtime, dependencies, and app code baked in layers. A container is a running instance of an image — like an object instantiated from a class. You can run multiple containers from one image. Images are built with docker build, containers are started with docker run. Images are stored in registries (Docker Hub, ECR, GHCR).
Docker builds images layer by layer. Each instruction (COPY, RUN) creates a layer. Docker caches layers — if a layer hasn't changed, it reuses the cached version. Key optimisation: copy package.json BEFORE source code. If source changes but package.json doesn't, npm install uses the cache (saving minutes). If you copy everything at once, any source change invalidates the npm install layer and re-runs it unnecessarily. Order layers from least-to-most frequently changing.
Running docker run for each service manually requires remembering all port mappings, environment variables, volume mounts, and network configuration. Docker Compose defines all services in one docker-compose.yml file. Benefits: (1) One command to start/stop entire stack (docker-compose up/down); (2) Services communicate by service name (e.g., mongodb://mongo:27017) on a shared network; (3) depends_on ensures startup order; (4) Easy to reproduce the exact environment for any developer or CI pipeline.
Multi-stage builds use multiple FROM statements. The first stage (build stage) can have dev dependencies and build tools. The final stage copies only the compiled output from the build stage, resulting in a much smaller production image. Example for TypeScript: Stage 1 installs all deps + compiles TS to JS. Stage 2 starts fresh with only Node:alpine, copies compiled JS, installs only production deps. Final image has no TypeScript compiler or source — much smaller and more secure.
🔑 Key Takeaways
  • Image = blueprint; Container = running instance
  • Copy package.json first in Dockerfile for layer caching
  • Use docker-compose to orchestrate multi-service local stacks
  • Run containers as non-root user for security
  • Use .dockerignore (like .gitignore) to exclude node_modules, .env

Deployment & DevOps

🔴 Must Know
🏭
Plain English — Factory Assembly Line Analogy

Without DevOps, releasing software is like a factory where workers manually carry products from station to station — slow, error-prone, inconsistent.

CI/CD is the automated assembly line. When you push code (git push), it automatically: runs tests, builds a Docker image, deploys to staging, runs smoke tests, then deploys to production — all without human intervention. If any step fails, the line stops. This is how Netflix deploys thousands of times per day safely.

🎤 Interview Q&A
Continuous Integration (CI): automatically run tests on every code push to catch bugs early, before they reach main branch. Continuous Deployment (CD): automatically deploy to production after tests pass — no manual steps. Benefits: (1) Faster feedback loop on bugs; (2) Prevents "merge hell" with frequent small integrations; (3) Consistent, repeatable deployments; (4) Rollback is easy (just redeploy previous Docker image); (5) Developers focus on features, not deployment logistics. Tools: GitHub Actions, GitLab CI, CircleCI.
Render/Railway (PaaS): managed platforms — you push code/Docker image, they handle servers, SSL, scaling. Zero server management. Higher cost per resource, but low ops overhead. Perfect for startups and side projects. VPS (DigitalOcean, Linode): raw Linux server — you configure Nginx, SSL (Let's Encrypt), PM2, firewall, everything yourself. Lower cost, full control, but significant ops knowledge required. AWS/GCP/Azure: enterprise cloud — EC2, ECS, Kubernetes. Maximum scale and flexibility, maximum complexity. Choose based on team size and operational capability.
Nginx is a high-performance web server/reverse proxy. Use cases with Node.js: (1) Reverse proxy — receives requests on port 80/443, forwards to Node.js on port 5000 (Node shouldn't run as root on port 80); (2) SSL termination — handles HTTPS/TLS, passes plain HTTP to Node; (3) Static file serving — serves React build files directly without hitting Node; (4) Load balancing — distributes requests across multiple Node processes; (5) WebSocket proxy — requires Upgrade header passthrough config. Much more efficient than Node for these tasks.
Strategies: (1) Rolling deployment: gradually replace old containers with new ones — load balancer routes to healthy instances; (2) Blue-Green deployment: run two identical environments (blue=current, green=new). Switch traffic to green instantly after validation. Blue becomes standby for instant rollback; (3) PM2 cluster mode: pm2 reload gracefully restarts workers one-by-one; (4) Health checks: only route traffic to instances passing health checks. Platforms like Render/Railway handle this automatically with their deployment pipeline.
🔑 Key Takeaways
  • CI = auto-test on every push; CD = auto-deploy on passing tests
  • Use GitHub Actions for free CI/CD with GitHub repos
  • Always add a /api/health endpoint for monitoring
  • Nginx sits in front of Node — handles SSL, static files, WebSocket proxy
  • Store all secrets in platform env vars — never in GitHub repo

AI Integration

🟣 Optional But Powerful
🧑‍✈️
Plain English — Co-Pilot Analogy

AI APIs are like having a brilliant co-pilot. The pilot (your app) still controls the plane — but for complex decisions like "what route avoids bad weather?" (e.g., "summarise this document"), you ask the co-pilot (GPT-4). You don't build the co-pilot from scratch — you just call them on the radio (API call).

The key skill isn't knowing machine learning — it's knowing how to integrate AI responsibly: prompt engineering, caching responses, handling failures, and not blocking your server while waiting for the AI.

📊 Production AI Integration Pattern
flowchart TD A[📱 Client Request\nanalyse task] --> B[⚙️ Node.js API] B --> C{🔴 Redis\nCached response?} C -->|✅ Hit| D[Return cached\nAI response] C -->|❌ Miss| E[📋 BullMQ\nAdd AI job] E --> F[👷 Worker] F --> G[🤖 OpenAI API\ngpt-4o-mini] G --> H[Parse + validate\nAI response] H --> I[Cache in Redis\nTTL 1 hour] I --> J[💬 Notify client\nvia Socket.IO]
javascript — OpenAI Integration with caching + queue 
const OpenAI = require('openai');
const client = new OpenAI({ apiKey: process.env.OPENAI_API_KEY });

// ── Cached AI call — never hit OpenAI twice for same input ──
async function cachedAICall(prompt, cacheKey, ttl = 3600) {
  const cached = await redis.get(cacheKey);
  if (cached) return JSON.parse(cached);

  const response = await client.chat.completions.create({
    model: 'gpt-4o-mini',       // Cheaper, faster than gpt-4
    messages: [
      { role: 'system', content: 'You are a helpful project management assistant. Always respond with valid JSON.' },
      { role: 'user', content: prompt }
    ],
    max_tokens: 500,
    temperature: 0.3,           // Lower = more deterministic
    response_format: { type: 'json_object' }
  });

  const result = JSON.parse(response.choices[0].message.content);
  await redis.setEx(cacheKey, ttl, JSON.stringify(result));
  return result;
}

// ── Route: AI breaks a goal into tasks ──
app.post('/api/ai/breakdown', authenticate, async (req, res) => {
  const { goal } = req.body;
  const cacheKey = `ai:breakdown:${Buffer.from(goal).toString('base64').slice(0, 40)}`;

  // Add to BullMQ — don't block HTTP response
  const job = await aiQueue.add('breakdown', { goal, userId: req.user.id, cacheKey });
  res.json({ jobId: job.id, message: 'AI is working on it...' });
});

// ── Worker: process AI job in background ──
new Worker('ai', async (job) => {
  if (job.name === 'breakdown') {
    const tasks = await cachedAICall(
      `Break down this goal into 5-7 specific, actionable tasks: "${job.data.goal}". 
       Return JSON: { "tasks": [{ "title": string, "priority": "high|medium|low", "estimate": string }] }`,
      job.data.cacheKey
    );
    // Notify client via Socket.IO
    io.to(job.data.userId).emit('ai-result', { type: 'breakdown', data: tasks });
  }
}, redisConfig);
🎤 Interview Q&A
OpenAI calls can take 5–30 seconds. Never await them in a route handler synchronously. Best approach: (1) Add to a BullMQ job queue — respond immediately with a job ID; (2) Worker processes AI call in background; (3) Notify client via Socket.IO when done. For streaming responses, use OpenAI's streaming API and pipe chunks via SSE. Also cache common AI responses in Redis to avoid redundant API calls entirely.
Prompt engineering is crafting the input to an LLM to reliably get useful, structured output. Key techniques: (1) System prompt — set context and output format (e.g., "always respond with JSON"); (2) Few-shot examples — show input/output pairs to guide format; (3) Temperature — lower (0.1-0.3) for factual/structured output, higher (0.7-1.0) for creative; (4) JSON mode — response_format: { type: 'json_object' } ensures parseable output. Good prompts reduce token usage and hallucinations.
(1) Cache responses — identical or similar prompts return cached result from Redis; (2) Use cheaper models — gpt-4o-mini costs ~20x less than gpt-4; (3) Rate limit per user — max N AI calls per day; (4) Truncate context — don't send entire chat history, summarise or use sliding window; (5) Set max_tokens — cap response length; (6) Monitor usage — set spend alerts in OpenAI dashboard; (7) Batch similar requests together when possible.
🔑 Key Takeaways
  • Always run AI calls in background workers — never block the HTTP thread
  • Cache AI responses in Redis — same input should never hit OpenAI twice
  • Use json_object mode for reliable structured output parsing
  • Rate limit per user + set spend alerts to control costs
  • Use gpt-4o-mini for most tasks — 95% quality at 5% cost of gpt-4

Architecture & Code Quality

🟠 Very Overlooked
🏗️
Plain English — Building Blueprint Analogy

Bad code architecture is like building a house without blueprints — everything works at first, but when you need to add a bathroom, you discover the pipes run through a load-bearing wall. You can't change one thing without breaking another.

Good architecture is the blueprint that makes each room (module) independent. You can renovate the kitchen without touching the bedroom. In code: separation of concerns means your database logic doesn't bleed into your route handlers. Each layer has one clear job.

javascript — Clean Layered Architecture (Express) 
// ── Folder Structure ──
// src/
// ├── routes/      user.routes.js     → just defines endpoints
// ├── controllers/ user.controller.js → handles req/res
// ├── services/    user.service.js    → business logic
// ├── models/      user.model.js      → DB schema
// ├── middleware/  auth.middleware.js
// ├── utils/       email.js, cache.js
// └── config/      db.js, redis.js

// ── routes/user.routes.js ──
router.post('/register', validate(registerSchema), userController.register);
router.get('/profile', authenticate, userController.getProfile);

// ── controllers/user.controller.js ──
// Only handles HTTP layer — no business logic here
const register = async (req, res, next) => {
  try {
    const user = await userService.register(req.body); // delegate to service
    res.status(201).json({ user });
  } catch (err) { next(err); } // pass to error handler
};

// ── services/user.service.js ──
// Pure business logic — no req/res, easily testable
const register = async ({ name, email, password }) => {
  const exists = await User.findOne({ email });
  if (exists) throw new AppError('Email already in use', 409);

  const hash = await bcrypt.hash(password, 12);
  const user = await User.create({ name, email, password: hash });

  await emailQueue.add('welcome', { to: email, name });
  return sanitizeUser(user); // never return password hash
};

// ── utils/AppError.js — Custom error class ──
class AppError extends Error {
  constructor(message, statusCode) {
    super(message);
    this.statusCode = statusCode;
    this.isOperational = true; // vs programming errors
  }
}

// ── Centralised error handler middleware ──
app.use((err, req, res, next) => {
  const status = err.statusCode || 500;
  const message = err.isOperational ? err.message : 'Internal Server Error';
  console.error(err); // log stack trace
  res.status(status).json({ error: message });
});
🎤 Interview Q&A
Separation of concerns means each part of the code has one clear responsibility. In Express: Routes define URL endpoints only. Controllers handle HTTP (req/res). Services contain business logic (no HTTP knowledge). Models define data shape. Why it matters: (1) Easy to test — services can be unit tested without HTTP; (2) Easy to change — swap MongoDB for PostgreSQL by changing only the model layer; (3) Easy to read — you know exactly where to find each type of logic; (4) Team collaboration — different devs can own different layers.
Use a centralised error handler middleware (4 argument function at the end of middleware chain). Throw/forward all errors to it with next(err). Create a custom AppError class with statusCode and isOperational. Operational errors (user not found, validation fail) return descriptive messages. Programming errors (null reference, syntax) return generic "Internal Server Error" to avoid leaking internals. Use process.on('unhandledRejection') to catch unhandled promise rejections globally.
S — Single Responsibility: one function/class does one thing (controller vs service vs model). O — Open/Closed: extend behaviour without modifying existing code (middleware chain — add new middleware rather than modify existing ones). D — Dependency Inversion: depend on abstractions, not concretions (inject services into controllers rather than hardcoding). In practice: keep functions small (under 20 lines), give them clear names, write them to be unit-testable, and prefer composition over inheritance.
(1) Always use async/await over callbacks or raw .then chains; (2) Wrap every async route handler in try/catch OR use an asyncWrapper higher-order function; (3) Never swallow errors silently — always log or rethrow; (4) Use Promise.all for parallel independent operations (don't await sequentially when not needed); (5) Validate inputs at the boundary (controller) before they reach services; (6) Keep service functions pure where possible — same input → same output, no hidden side effects.
🔑 Key Takeaways
  • Structure: Routes → Controllers → Services → Models
  • Services contain business logic — no req/res, easily unit-testable
  • Use a centralised error handler — no scattered try/catch everywhere
  • Custom AppError class: distinguish operational vs programming errors
  • Keep functions small, single-purpose, and named clearly
